# mem-manager 设计文档（中文）

> 本文档描述 mem-manager 的整体设计：**两步走机制**——第一步 Profiling（采集真实分配行为，已完成），
> 第二步 内存池分配方案（基于采集数据，JSON 配置文件驱动；**v1 bump 池已实现并进入内部试用**）。
> 英文版架构说明见 `DESIGN.md`，Step 1 细节见 `STEP1.md`。

---

## 1. 背景与目标

### 1.1 问题
业务平台封装了操作系统的共享内存原语 `ShmMap` / `ShmMapOnPg` / `ShmUnmap`。
**OS 分配共享内存的最小粒度是 2MB**。而业务会申请大量**远小于 2MB 的小块**，
每个小块都被 OS 撑成一个完整的 2MB 区域 → 内存严重浪费。

### 1.2 实测浪费（已用 OS 全量 shm 日志交叉验证）
| 指标 | 数值 |
|---|---|
| 不同共享内存区域数（按 shmname 去重） | ~14,467 |
| 实际申请总量 | ~1.3 GB |
| OS 实际占用（每块按 2MB 对齐） | ~28.8 GB |
| **浪费** | **~27.5 GB（约 95%）** |
| 平均每块大小 | ~94 KB（远小于 2MB） |

分配大小分布的主体集中在 **16KB–256KB**，几乎全部 < 2MB，每块都在 2MB 粒度上浪费 ~95%。
`14467 × 2MB ≈ 28.9GB` 与 OS 实测 28.8GB 吻合，确认"小块占满 2MB"就是浪费来源。

### 1.3 目标
**预先申请大块共享内存作为"池"，从池中自管理地切分小块给业务使用**，
把 OS 占用从 ~28.8GB 压向接近真实需求的 ~1.3GB（潜在 ~20 倍下降）。
池的大小与结构**通过配置文件配置**，便于随需求演进调整，无需改代码重编。

## 2. 两步走机制总览

```
Step 1（已完成）  采集                    Step 2（待实现）  分配
┌─────────────────────────────┐        ┌─────────────────────────────┐
│ Platform_ShmMap 透传 OS 调用 │        │ Platform_ShmMap 改为：       │
│   + 记录每次分配的            │        │   小块 → 从内存池切分        │
│   size / flags / 名字 / 时间 │ ───→   │   大块 → 透传给 OS           │
│ 离线分析得出真实分配画像     │        │ 池的大小/结构由配置文件决定  │
└─────────────────────────────┘        └─────────────────────────────┘
```

两步共用**同一套对外接口** `Platform_ShmMap` / `Platform_ShmMapOnPg` / `Platform_ShmUnmap`：
- Step 1：接口=纯透传 + 旁路采集；
- Step 2：接口内部改为"小块走池、大块透传"，**业务代码无需改动**。

## 3. Step 1：Profiling（已完成）

### 3.1 包装层
对外三个包装函数，行为与 OS 完全一致（透传），仅在 Debug 构建（宏 `MEM_MANAGER_PROFILE`）下额外采集：

| 包装函数 | 透传到 | 说明 |
|---|---|---|
| `Platform_ShmMap` | `ShmMap` | 申请/映射共享内存 |
| `Platform_ShmMapOnPg` | `ShmMapOnPg` | 在 pgname 所在 NUMA 节点上分配（**仅控制面 CP 有此符号**） |
| `Platform_ShmUnmap` | `ShmUnmap` | 解除映射（仅地址，map/unmap 靠返回地址关联） |

- 公共头 `platform/platform_shm.h` 带 `extern "C"`，C++ 控制面也能调。
- 实现是 **C（C11）**，因为数据面 DP 是纯 C 环境、无 C++ 运行时。

### 3.2 平面区分：CP vs DP
系统分两个平面，由业务自有的 **`IS_CP` 宏**区分（CP 定义、DP 不定义）：

- **控制面 CP**：单进程，平台把 N 个业务 .so dlopen 进来；有完整 libc。
- **数据面 DP**：绑核（NUMA/核亲和）、按进程组（pg/vcpu）运行；**无 libc、无标准函数名**。

mem-manager 直接按 `IS_CP` 适配：
- `#ifdef IS_CP` → 编译 `Platform_ShmMapOnPg`（DP 无 `ShmMapOnPg` 符号，必须编掉，否则 DP 链接报 undefined）；
- profiler 后端也按 `IS_CP` 选择（见 3.4）。

### 3.3 防绕过：门面头 + poison
为保证**所有分配都经过包装层**（否则采集/池子都会漏），提供业务侧入口头
`platform/platform_shm_api.h`：它暴露 OS 常量 + `Platform_Shm*`，并用
`#pragma GCC poison ShmMap ShmMapOnPg ShmUnmap` 把原始 OS 调用**毒化**——
业务再直接写 `ShmMap` 会编译报错，强制走 `Platform_ShmMap`。
（实现 `platform_shm.c` 不包含此门面头，照常调用真正的 OS 函数。）

### 3.4 两个 profiler 后端
DP 无 libc、且其日志路径自身会用 ShmMap，所以分两个编译期后端：

- **CP（默认）**：有 libc，直接 `open/write` 写每进程 JSONL 文件，内联算出生命周期/峰值。
- **DP（`IS_CP` 不定义）**：无状态，把每个事件拼成一行 JSON，交给 OS 的
  `LOG_FILE_INFO(module, ...)` 宏输出（module 默认 `SHMPROF`，本项目用 `SHMPROF_XIL`）。
  时间/身份由日志前缀自带（CP 墙钟、DP `[pg][vcpu][TSC]`），离线还原。
  仅依赖 `LOG_FILE_INFO` + 编译器生成的 `memcpy`。

### 3.5 离线分析
`tools/analyze_profile.py`：吃 CP 的 JSONL 和 DP 的日志行（按 module 过滤、解前缀），
按 `shmname`/`[pg][vcpu]` 关联 map↔unmap，输出：大小分布、**2MB 浪费 KPI**、
按名字去重的真实物理占用、峰值同时存活（池大小下界）、生命周期、flags/VA 分类等。

`tools/crosscheck_os_log.py`：拿 OS 全量 shm 日志（每行 `[ts] addr 申请size 对齐size … shmname`，
**size 列是无 0x 前缀的十六进制**，工具自动识别）交叉验证我们采集的 size 与 2MB 对齐是否一致。

### 3.6 关键发现（指导 Step 2）
1. **浪费 ~95%**（1.3GB vs 28.8GB），主体是 **<2MB 的小块**，集中在 16K–256K。
2. **`ShmMap` 返回值是引用数**：`ret>0` 成功（值=该 shm 的引用计数）、`ret<0` 失败，**CP/DP 都如此**。
3. **flags 编码共享范围与 VA 语义**：4/5=VA-same（裸指针跨进程有效）、0/1/2=VA-differs（须用偏移）、3=进程共享。
   **实测（2026-07 修正）：业务几乎全是 VA-differs（0/1/2）**，早期"~99% VA-same"的数据有误。
   硬约束：**不同 flags 值（共享范围/VA 类别不同）不能放进同一个池块**。
4. 共享内存被多个上下文各映射一次，所以"映射次数"远多于"物理区域数"——池子只需按**物理区域**（去重）算容量。

## 4. Step 2：内存池分配方案（设计）

### 4.1 总体思路
`Platform_ShmMap(flags, name, size, &p)` 内部改为：

```
请求进来
  │
  ├─ size ≥ 阈值 pool_threshold ？ ──是──→ 直接透传 OS ShmMap（大块不进池）
  │                                          （>2MB 的大块本来就要≥2MB，浪费小）
  ├─ flags 不在可池化掩码里（默认仅 {1}；3/未启用的 flags）？ ──是──→ 透传 OS
  │
  └─ 否则（小块 + 可池化 flags）：
        ├─ name 已在池中？ ──是──→ 返回同一槽位（名字共享，引用数+1）
        └─ 否 ──→ 从对应 flags 的池块中切一个槽位，登记 name→(池块,偏移)，返回指针
```

- **池块（pool block）**：预先用真正的 OS `ShmMap` 申请的大块（如 2MB 或更大，可配），是池的"原料"。
- **槽位（slot）**：从池块中切出的小格（v1 用 bump 精确切分，无大小类），分给业务。
- **VA-differs 直接池化**（2026-07 修正，业务几乎全是 VA-differs）：共享注册表只存
  `(池块, 偏移)`、不存指针；各进程按池块名自行 attach、用本地 VA + 偏移得到地址。
  同一路径对 VA-same 也成立。

### 4.2 池结构：v1 = bump，大小类/slab 留作演进

> **2026-07 范围更新**：v1 只实现 **bump**（指针推进、精确无内碎片、不回收槽，
> 契合 init-once/长生命周期画像）；下面的大小类/slab 结构保留为后续演进设计。

为减少内部碎片，按请求大小分若干"大小类"，每类独立成池（类似 slab 分配器）：

```
大小类示例（可配）： 16K, 32K, 64K, 128K, 256K, 512K, 1M
  每个大小类：
    ├─ 若干"池块"（每块来自一次 OS ShmMap，块大小可配，如 2MB）
    │     池块 = ⌊块大小 / 类槽大小⌋ 个槽位
    ├─ 空闲槽位链表（free list）
    └─ 不够用时按"增长策略"再申请新池块
```

- 一个 2MB 池块在 64K 类里可放 32 个槽，在 256K 类里可放 8 个槽。
- 申请 90KB → 落入 128K 类，给一个 128K 槽（仍比独占 2MB 省 16 倍）。
- 这正契合实测分布（主体 16K–256K）。

> 备选结构（后续可选）：单一池 + 通用 bestfit/buddy 切分。slab 实现简单、无外部碎片、释放快，
> 作为 v1 首选；若大小分布很分散再考虑 buddy。

### 4.3 名字共享与引用计数
OS 的 shm 是**按名字共享**的：多个上下文 `ShmMap` 同一个 name 得到同一块内存。
池子要保留这个语义：

- `Platform_ShmMap` 内维护 **`shmname → (池块, 偏移, 大小, 引用数)` 注册表**。
- 首次 `ShmMap(name)`：分配槽位、登记、引用数=1。
- 再次 `ShmMap(name)`（同名 attach）：返回同一槽位、引用数+1，**返回值=引用数**（与 OS 约定一致）。
- `Platform_ShmUnmap(addr)`：按地址查到槽位，引用数-1；减到 0 才真正回收槽位到 free list。

### 4.4 NUMA / DP（OnPg）
`Platform_ShmMapOnPg(pgname, …)` 要求内存落在 pgname 所在 NUMA 节点。
→ **每个 NUMA 节点一套池**，池块用 `ShmMapOnPg` 在对应节点申请；按 pgname 路由到对应池。
（CP-only 符号，DP 构建不编 OnPg。）

### 4.5 并发
采集阶段已确定**默认线程安全**。池分配涉及 free list/注册表的并发修改，
**必须加锁**（每个大小类一把锁，降低争用；或无锁 free list，后续优化）。
锁与原子操作统一使用平台提供的 `AAA_*` 接口（独立构建时在 `os_shm_stub.c` 用 C11 stdatomic 提供等价实现）。

### 4.6 初始化与生命周期
- 业务语义是**系统初始化时申请、停止时释放**（无频繁 map/unmap churn），所以池更偏"一次建好、长期持有"。
- **谁读配置**：由能做文件 I/O 的一方（CP / 平台初始化）在启动时读配置文件、建立池元数据。
- **元数据放哪**：池的元数据（大小类表、池块列表、free list、name 注册表）放在一块**专用共享内存**里
  （用真正的 ShmMap 以固定名字申请），CP/DP 都 attach 到同一份，**DP 不需要读文件**。
- 池块本身也是共享内存，业务拿到的指针就指向池块内的槽位。

## 5. 配置文件设计

### 5.1 为什么用配置文件
池的阈值、块大小、大小类、每节点容量等会**随业务需求变化**。用配置文件可在**不改代码、不重编**的情况下调整，
便于在不同部署/不同业务下调优。

### 5.2 加载机制
- 配置文件由 **CP / 平台初始化**阶段读取（有 libc / 文件 I/O）。
- 解析后的参数写入"池元数据共享内存"，**DP 启动时 attach、不直接读文件**（DP 无 libc/文件系统）。
- 配置文件路径通过环境变量或平台已有配置入口指定（如 `MEM_POOL_CONFIG`）。

### 5.3 配置项（v1，JSON）
```json
{
  "enable": true,                // 总开关；false 时全部透传 OS（等价 Step 1 行为）
  "threshold": "0x200000",       // 阈值：请求 ≥ 此值直接透传 OS（默认 2MB）
  "block_size": "0x4000000",     // 池块大小（一次 OS ShmMap 的粒度，默认 64MB）
  "poolable_flags": [1]          // v1：默认只池化 flags=1（VA-differs，CP+DP 进程组间），其余透传
}
```
（完整示例见仓库 `config/pool.json`。大小可写 JSON 数字或 `"0x.."` 字符串；
大小类/多池等扩展键待后续按真实数据引入。）

设计原则：
- **可演进**：JSON 可随时加键；未知键忽略，向后兼容。
- **单位统一**：尺寸用十六进制字节字符串（与 OS 日志一致，避免歧义）。
- **缺省安全**：缺配置时用内置缺省；`enable=false` 时退化为纯透传，零风险回滚。
- **优先级**：内置缺省 < JSON 文件 < `MEM_POOL_*` 环境变量（`MEM_POOL_ENABLE=0` 永远是一键回滚）。

### 5.4 格式选择（2026-07 定为 JSON）
用**扁平 JSON 对象**，CP 端手写极简解析（`mm_pool_load_config`，几十行、无第三方库、
只认扁平键值 + 整数数组，不实现完整 JSON 语法）：
- 人类可读、可与平台其它 JSON 配置统一；
- 解析只在 CP/元数据创建方发生，DP attach 元数据 shm 即可，无需在 DP 读文件。

## 6. 关键约束与不变量

1. **DP 必须是 C**：整个实现 C11，DP 无 C++ 运行时。
2. **不同 flags 值不能共池块**（硬正确性约束：共享范围/VA 类别不同）；v1 默认只池化 flags=1（VA-differs），
   元数据只存偏移、各进程本地解析 VA，process-shared（3）与掩码外 flags 透传。
3. **阈值以上、大块透传**：>2MB 本来就要 ≥2MB，进池无收益。
4. **名字共享语义不能破坏**：同名 attach 必须拿到同一块；引用计数正确；引用数=返回值。
5. **行为对业务透明**：业务只认 `Platform_ShmMap`，内部走池还是透传不影响其使用。
6. **可一键回滚**：`enable=false` 退化为 Step 1 的纯透传。注意前提：配置是创建者写进共享 meta 的快照，
   回滚须在所有进程退出、meta 区域销毁重建后才生效（attach 方不读自己的配置）。
7. **线程安全**：池操作加锁。
8. **同名不双映射**：可池化名字在并发创建未决时绝不透传 OS（有界自旋 + 重查注册表），
   杜绝同一名字同时存在于池和 OS；attach 与注册项不一致（flags/size）明确报错。

---

## 7. 演进与未决问题

- **可池化范围扩展**：默认仅 flags=1；若实测需要，把 0/2（VA-differs）甚至 4/5（VA-same）加进
  JSON 配置的 `poolable_flags` 即可，同一条寻址路径已支持，无需改代码。
- **大小类划分**：初版按实测分布（16K/64K/256K/1M）；上线后据真实数据微调（配置文件即可）。
- **碎片与回收**：init-once 场景碎片压力小；若出现频繁 map/unmap，再评估槽位回收/合并策略。
- **元数据共享内存的崩溃恢复**：进程异常退出后池状态一致性（引用数泄漏）如何处理。
- **跨 NUMA 的池容量分配**：按 pgname/节点分配多少初始块。
- **配置热更新**：是否支持运行时改配置（一般只在初始化生效即可）。
